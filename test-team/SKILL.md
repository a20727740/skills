# test-team: 并行分析与测试团队

创建一个四人并行工作团队，同时对当前项目进行全方位分析与优化。四个角色同时推进，持续汇报各自的发现和修复进度。

## 团队角色

| 角色 | 代号 | 职责 |
|------|------|------|
| 程序员 | `DEV` | 核心架构分析、问题定位、修复方案设计与实施 |
| 测试员 | `QA` | 功能测试、问题复现、边界条件验证、回归测试记录 |
| 内存检测员 | `MEM` | 内存泄漏检测、性能瓶颈分析、资源占用优化建议 |
| UI 设计师 | `UI` | 界面布局审查、交互体验优化、视觉一致性检查 |

## 参数说明

- `--focus <role>`：仅启动指定角色（`DEV` / `QA` / `MEM` / `UI`），不传则全部启动
- `--issue <描述>`：指定要分析的具体问题，不传则对项目进行整体扫描

## 执行流程

### 第一阶段：项目扫描（全员并行）

所有角色**同时启动**，各自独立扫描项目，互不阻塞。

#### DEV - 程序员扫描

1. 读取项目架构文档（`.claude/rules/architecture.md` 或 `CLAUDE.md`）
2. 扫描核心源码文件，分析：
   - 模块依赖关系是否合理
   - 是否存在循环依赖
   - 错误处理是否完善
   - 数据流方向是否清晰
   - 是否有潜在的安全隐患（注入、XSS、越权等）
3. 如果指定了 `--issue`，重点分析问题相关代码路径
4. 输出格式：
   ```
   [DEV] 架构分析报告
   ├── 模块结构评估：...
   ├── 发现的问题：
   │   1. [严重程度] 问题描述 → 文件:行号
   │   2. ...
   └── 修复方案：
       ├── 方案A（推荐）：...
       └── 方案B（备选）：...
   ```

#### QA - 测试员扫描

1. 识别项目的主要功能入口和用户交互路径
2. 检查测试文件（`Tests/`、`__tests__/`、`*_test.*`、`*.test.*` 等）
3. 分析测试覆盖率，识别：
   - 缺少测试的核心功能
   - 边界条件未覆盖的场景
   - 异常路径未测试的分支
4. 如果指定了 `--issue`，设计针对性的复现步骤
5. 输出格式：
   ```
   [QA] 功能测试报告
   ├── 测试覆盖现状：...
   ├── 未覆盖的关键场景：
   │   1. 场景描述 → 建议测试用例
   │   2. ...
   ├── 问题复现记录（如有）：
   │   ├── 步骤1：...
   │   ├── 预期结果：...
   │   └── 实际结果：...
   └── 回归风险评估：...
   ```

#### MEM - 内存检测员扫描

1. 检查项目是否已有内存检测机制（LeakDetector、Instruments 等）
2. 扫描常见内存问题模式：
   - **循环引用**：闭包捕获 `self` 未使用 `[weak self]`、delegate 强引用、NotificationCenter 未移除观察者
   - **资源泄漏**：文件句柄未关闭、数据库连接未释放、定时器未销毁、URLSession 未取消
   - **性能瓶颈**：主线程阻塞（同步 I/O、大量计算）、不必要的重绘、过度刷新 UI
   - **内存增长**：缓存无上限、集合无限增长、大对象未及时释放
3. 针对当前技术栈使用特定的检查策略：
   - **Swift**：检查 `@escaping` 闭包、`weak/unowned` 使用、Combine 订阅管理
   - **JavaScript/TS**：检查事件监听器清理、闭包引用、定时器
   - **Python**：检查循环引用、全局缓存、生成器使用
4. 输出格式：
   ```
   [MEM] 内存与性能报告
   ├── 检测概况：扫描 N 个文件，发现 M 个风险点
   ├── 内存风险：
   │   1. [高/中/低] 问题描述 → 文件:行号
   │   └── 修复建议：...
   ├── 性能瓶颈：
   │   1. [高/中/低] 问题描述 → 文件:行号
   │   └── 优化建议：...
   └── 资源管理评估：...
   ```

#### UI - UI 设计师扫描

1. 分析项目 UI 组件结构和布局代码
2. 检查以下方面：
   - **布局一致性**：间距、字号、颜色是否统一使用主题系统
   - **交互体验**：操作反馈（loading、成功、错误）、快捷键支持、无障碍访问
   - **响应式适配**：窗口缩放、多屏幕、暗色模式支持
   - **视觉细节**：对齐方式、截断策略、空状态处理、加载占位
3. 使用 `/ui-ux-pro-max` skill 进行专业 UI/UX 分析（如果可用）
4. 输出格式：
   ```
   [UI] 界面与交互报告
   ├── 设计系统一致性：...
   ├── 交互问题：
   │   1. 问题描述 → 组件/文件位置
   │   └── 优化建议：...
   ├── 视觉问题：
   │   1. 问题描述 → 具体位置
   │   └── 优化建议：...
   └── 优先级排序：...
   ```

### 第二阶段：交叉评审（团队协作）

各角色完成扫描后，进行交叉评审：

1. **DEV** 审查 QA 和 MEM 发现的问题，评估修复优先级和工作量
2. **QA** 根据 DEV 和 MEM 的修复方案，补充回归测试计划
3. **MEM** 审查 DEV 提出的修复方案，评估是否引入新的内存/性能问题
4. **UI** 审查修复方案是否影响界面表现，提出视觉回归检查点

输出交叉评审摘要：
```
[TEAM] 交叉评审摘要
├── 修复优先级排序：
│   P0（立即修复）：...
│   P1（本次迭代）：...
│   P2（后续优化）：...
├── 依赖关系：某些修复需要按顺序执行
│   ├── 先修复 A，再修复 B（因为 B 依赖 A 的改动）
│   └── ...
└── 风险提示：...
```

### 第三阶段：执行修复（按优先级）

按 P0 → P1 → P2 的优先级依次执行修复：

1. 每个修复前，标注影响范围和预计变更文件
2. 修复完成后，相关角色验证：
   - **DEV** 确认代码编译通过
   - **QA** 确认测试覆盖
   - **MEM** 确认无新增内存/性能风险
   - **UI** 确认界面无回归
3. 使用 `TodoWrite` 实时更新进度

### 第四阶段：总结报告

输出最终团队报告：
```
[TEAM] 最终报告
├── 项目健康度评分：X/100
├── 已修复问题：N 个
│   ├── P0：N 个 ✓
│   ├── P1：N 个 ✓
│   └── P2：N 个（建议后续处理）
├── 遗留问题：N 个（附原因和后续建议）
├── 各角色关键指标：
│   ├── [DEV] 代码质量提升：...
│   ├── [QA] 测试覆盖率变化：...
│   ├── [MEM] 内存风险消除：...
│   └── [UI] 交互体验改善：...
└── 后续建议：
    1. ...
    2. ...
```

## 重要规则

1. **并行优先**：第一阶段四个角色必须并行启动，使用 Task 工具同时创建多个 agent，不要串行执行
2. **实时汇报**：每个角色完成扫描后立即输出报告，不要等所有角色完成
3. **量化评估**：所有问题必须标注严重程度（高/中/低）和具体文件位置
4. **可执行方案**：每个问题必须附带具体的修复建议，不要只描述问题
5. **使用 TodoWrite**：全程使用任务列表跟踪进度，每个角色的扫描、修复、验证都作为独立任务项
6. **增量修复**：修复按优先级分批进行，每批修复后验证，不要一次性大改
7. **最小改动原则**：修复方案优先选择最小侵入性的方案，避免过度重构
8. **技术栈适配**：根据项目实际技术栈调整检查策略和代码示例
